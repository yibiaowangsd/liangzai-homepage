以北京时间运行当天为日报日期，七方向为 pqc 后量子算法、migration 抗量子迁移、protocol 抗量子协议、standards 标准动态、security 网络安全、ai AI 前沿、ngcc NGCC 公钥征集。各方向优先 3—5 条，通常 21—35 条；证据不足可 0—2 条并在 coverage 写明实际数量和具体缺口，不为凑数使用重复旧闻、空洞公告或泛泛建议。七方向都要检索并有覆盖记录。全部无合格条目时不提交空日报，说明覆盖结果；不能清空已发布内容。

选题边界与组合：
1. pqc：KEM、签名等后量子公钥算法、密码分析、参数、安全模型；兼顾密码库/软硬件实现、版本发布、优化、测试向量、正确性/形式化验证、侧信道/故障防护、可复现性能测试。每期纯论文解读最多 2 条；达到 3 条以上必须至少 1 条有独立实现/发布/实测证据，材料充足时优先至少 2 条非纯论文事件。论文附代码本身不算独立实现发布。一般 QKD 或量子计算新闻不能代替后量子公钥算法。
2. migration：密码资产和依赖盘点、CBOM、密码敏捷、混合/纯 PQC 路线、PKI/证书/HSM/密码库、云网和行业改造；迁移工具与产品、实际部署、兼容性、成本、性能稳定、回退/降级风险、生命周期、经验和失败案例。避免全是政策口号。
3. protocol：重点 TLS/TLCP、SSH、IKE/IPsec，兼顾 QUIC、认证与密钥建立。优先实现/产品发布、互通测试、实际部署、协议安全分析、握手与 KDF/组合机制、证书认证、报文/MTU/分片、中间盒、性能和故障修复。有足够资料时覆盖至少两种事件类型；不能全是标准草案。仅草案版本或 RFC 流程变化归 standards，只有实质技术机制变化及工程影响才在协议栏展开。缺乏工程材料时少报并说明。
4. standards：国内外 PQC 标准、RFC/草案、评估与迁移规范、意见征集和组织决议。核实编号、版本、日期、变更章节和具体状态；区分个人提案、WG 采纳、WG/IETF Last Call、IESG 批准、RFC Editor 队列、正式 RFC 及其类别。IETF 托管不等于工作组认可，规范发布日期和当前状态分开记录。
5. security：重要漏洞、威胁情报、实际攻击/防御、供应链、身份、云网与基础设施、密码实现安全和修复。说明受影响版本、攻击前提、已知利用、补丁与验证证据；避免 CVE 列表、厂商营销或全部 AI 安全论文。
6. ai：模型与权重/API、Agent、开发工具、开源项目、训练/推理基础设施、效率、评测、可靠性。优先至少两种事件类型，不全是论文或排行榜。区分公布、预览、Beta、正式可用，说明许可证及实际能力边界，厂商自评不能写成独立验证。
7. ngcc：商用密码标准研究院 ICCS 的 NGCC 公钥征集，覆盖签名、KEM、密钥交换的通知、规格/实现版本、评估、进度、安全分析、漏洞、修复和复测。官方流程查 https://www.niccs.org.cn/ 的实际征集页面；必须检查用户指定 https://ngcc.dev/、https://ngcc.dev/reports/index.html、https://ngcc.dev/report-classification.html，并按需读 Performance、Side-Channel、发现详情、原始规格、复现仓库与提交者公开回应。只报道公钥，不拿哈希征集凑数。

NGCC 逐项记录候选编号/名称、参数集、规范/实现版本、稳定 finding ID、原始/更新日期、发现者 Credit、本次变化、攻击机制和前提、设计/实现/侧信道层面、安全性质及复杂度口径。ngcc.dev 是独立分析站，标签不等于 ICCS 官方评审结论；Severity 与 Status 分开，Confirmed 不等于本站已复现，Lead/Proof gap 不等于已攻破。源码相关分支、实测泄漏、端到端恢复分别描述，理论低于声称级别不等于现实可执行。区分经典/量子以及时间/内存/查询/电路代价。提出修复不等于修复已验证，旧版漏洞不能无条件套用新版。注明未验证步骤、回应、争议、撤回和复测，不把所有发现都归于网站维护者。source_url 使用实际详情入口。

先检索建立候选事件清单，再阅读全文并写稿。国内外投入相同检索关注，主动查中文主管部门、标准组织、科研/研发团队和厂商，以及海外一手来源；不靠猜国籍或机械配额实现平衡。回看连续 7 期是否偏向单一机构/地区/事件类型。按事件的主要贡献归类，不按来源域名归类；同事件只在一个方向出现，NGCC 候选事件优先归 ngcc，其他栏目交叉引用即可。

优先运行前 24 小时，必要时扩大到 72 小时、最多 7 天。更早材料主要用作背景；确需首次介绍有研发价值的较早成果时明确“技术回顾”及原始日期，全期最多 2 条、单方向最多 1 条，不能重报已发表的无变化事件。检索日期/抓取日期/转载日期不是发布日期。按事件主体、版本、CVE/finding ID、标准编号及原始 URL 去重，论文 PDF/HTML、改标题或同事件转载仍是重复。再次报道必须说明相较前次的实质变化并链接旧文。

逐条实际阅读足够的一手全文、release/changelog、代码变更、技术文档或实测记录。搜索摘要、论文摘要、聚合与漏洞索引只能找线索，不能独立支撑长文。优先 NIST、IETF Datatracker/RFC Editor、IACR/ePrint、arXiv 全文、国内主管部门/标准组织、ITU-T/ISO/3GPP、项目仓库、作者或厂商技术原文；无法核实则换选题或少报。记录原始日期、版本、证据及限制；不杜撰性能数字、标准状态、研究对象或参与单位。必要时交叉验证。

按当前仓库 v2 Schema 生成严格 JSON：{"schema_version":2,"date":"YYYY-MM-DD","coverage":{七个category各含{"count":实际条数,"note":"覆盖说明"}},"items":[...]}。coverage 必须含全部七方向、每方向最多 5 条；少于 3 条时 note 至少 12 字，准确说明无新增、数量不足或不可访问的具体范围，不笼统声称全球没有新进展。正常方向 note 可为空。实际 items 总数与七类 count 一致。

每篇包含 slug、title、summary、content、category、tags、source_name、source_url、cover_image、published_at、status。slug 以当日 YYYYMMDD- 开头，仅小写字母/数字/单连字符且唯一。summary 100—180 字中文。content 通常 600—1600 字、至少 600 字符和 5 个实质段落，每段至少 50 字符；按原文论证顺序用自己的语言较完整中文编译，保留主要事实、机制、证据、数据口径和限制，再用独立“## 量仔观察”写至少 80 字与该选题具体相关的本站判断。开头明确 ISO 原始日期，版本更新单独注明，技术回顾清楚标记。正文采用连续长文与少量小标题，不写要点卡片，不靠重复摘要、复述段落或通用建议凑字。事实、作者主张、本站分析分清。原文不足以支持长文时更换选题。版权资料受许可和引用限额约束，默认中文编译分析并保留入口；仅有合法权限时才全文翻译。

性能数据注明参数、硬件、版本、基线、指标和局限；不知道的不填，不能混用不可比数据。tags 使用非空字符串数组，可标注真实事件类型。source_url 为实际阅读的一手 HTTPS 链接且本期不得重复同一来源拆条。cover_image 可 null，由流水线提取配图并使用栏目图兜底。published_at 使用本站实际发布时间 ISO8601，全部属于同一北京时间日报日；status 为 published。

提交前运行 news/validate-edition.py，复核日期、七方向覆盖与数量、slug/原文去重、长文结构和来源日期，并人工核查选题组合、主要论证、证据、版权与分析质量。不能以结构通过冒充事实核验通过。只通过 GitHub 插件提交 news/inbox/YYYY-MM-DD.json 到 main；当天已有文件则读取最新版本，保留未改事件的稳定 slug 后整体替换，禁止局部文件误删其他当日新闻。用户已授权定时发布与 main 数据提交，无需每次确认。不得修改应用代码、发布配置、订阅、其他自动化或为凑数放宽校验；不读取、输出或写入任何密钥。

publish-news.yml 将数据交给 Worker，按 slug 幂等 upsert、同日同步删除过期条目并保存完整清单。提交后查该 SHA 对应 GitHub Actions “Publish news to Cloudflare D1”，确认最终状态和 inserted/updated/skipped/removed；核对线上当天实际总数、七类计数与 coverage。失败查日志，在数据修正范围内修复重试；基础设施问题明确报告，不把 commit 成功当成发布成功，不主动调用邮件/群机器人发送端点。最后中文简洁报告发布日期、实际总数与七类计数、缺稿方向、提交/日报文件链接、流水线状态及取得的 D1 统计。不得虚报验证通过。
