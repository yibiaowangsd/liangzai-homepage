# 每日前沿选编规则

自 2026-10-11 起适用，2026-10-19 修订。目标是帮助密码、网络安全与AI研发及产业读者理解有证据的实质进展。信息源和具体检索入口见 [来源指南](source-guide.md)，与 [日报任务提示词](daily-automation-prompt.md) 同步执行。新闻价值、事实与新增程度优先，不能把栏目变成论文目录、标准索引、固定密码库/推理框架的提交记录或厂商新闻稿合集。

## 八个同级栏目与归类边界

| category | 方向 | 选题范围与边界 |
| --- | --- | --- |
| pqc | 后量子算法 | KEM、数字签名及其他后量子公钥构造。以算法层面的实质进展为主线：新构造与技术路线、数学假设与安全模型、归约与安全证明、密码分析及攻击复杂度、参数与安全级别、密钥/密文/签名尺寸、效率与算法多样性。来源同时覆盖高校/科研机构的论文与学术成果，企业的算法研发、技术报告、产品所含算法能力和专用软硬件成果，政府/主管部门/评估机构发布的算法研究、技术评测、安全分析和遴选依据。学术成果不要求先有代码、产品或生产部署，必须阅读全文并区分初步主张、证明、实验与独立验证。实现、密码库发布、测试向量、形式化验证、侧信道/故障防护和可复现基准仍可报道，但不能以GitHub提交或算法库小修复代替整个算法方向。企业迁移方案归migration，纯政策/标准流程归standards，NGCC候选归ngcc；一般QKD或量子计算新闻不能代替后量子公钥算法。 |
| migration | 抗量子迁移 | 国内外公司的迁移工作与技术方案：架构/解决方案、技术白皮书、路线图、产品能力与版本、咨询与密码资产评估服务、CBOM/依赖盘点工具、密码敏捷、混合/纯 PQC 路线、PKI/证书/HSM/密码库适配、云网与行业改造、合作项目、试点/互通测试、分阶段实施经验及失败案例。已公开且有实质技术细节的新方案或工作进展即可报道，不要求先有代码发布或生产上线；区分提出、计划、预览、试点、产品可用与生产部署，解释适用对象、实施机制、交付阶段、兼容性、性能/成本与回退风险。 |
| protocol | 抗量子协议 | TLS/TLCP、SSH、IKE/IPsec 为重点，兼顾 QUIC、认证与密钥建立协议。关注实现/产品发布、协商与认证机制、组合/KDF、互通测试、握手和报文开销、MTU/分片、中间盒、故障与修复、协议安全分析和实际部署。状态变化本身归 standards；只有实质技术机制变更及其工程影响才在本栏深入分析。 |
| standards | 标准动态 | 国内外 PQC 标准、RFC、草案、征求意见、评估方法、迁移规范与组织决议。核实编号、版本、日期、制定组织、状态、变更章节和下一里程碑。个人提案、WG 文档、WG/IETF Last Call、IESG 批准、RFC Editor 队列与正式 RFC 必须区分；正式 RFC 也要说明类别。NGCC 征集通知优先归 ngcc。 |
| security | 网络安全 | 重要漏洞、实际攻击/威胁情报、防御、供应链、勒索/泄露、身份、云网/工控/基础设施、密码实现安全、补丁和事故复盘；兼顾受影响机构回应、监管及执法公开结果。说明影响版本、前提、利用证据、缓解及修复，不罗列CVE或营销，普通bug不自动为安全漏洞。NGCC漏洞归ngcc，不能用AI安全论文或代码维护填满此栏。 |
| ai | AI 前沿 | 模型/权重/API、多模态/Agent、开发工具、开源项目、推理/训练/芯片与算力、效率/成本、真实应用、可靠性/安全、原始独立评测及影响技术采用的政策、许可证和产业变化。明确许可、可用阶段、测试配置与限制；厂商自评不是独立验证，不以论文、排行榜或推理框架维护填栏。商业新闻须有技术供应/采用/成本的实质关联。 |
| ngcc | NGCC 公钥征集 | 商用密码标准研究院（ICCS）NGCC 公钥征集：签名、KEM、密钥交换的通知、候选规格/实现版本、评估与进度、安全分析、漏洞、修复和复测。只关注公钥，不以哈希征集或其他赛事凑数。 |

| flash | 快讯 | 重要且能独立核实的简明公告、发布/可用性、许可、征求意见节点、行业采用及处置更新；使用短稿直陈事实、日期与影响，主题写在tags。不是低价值维护或未证实线索的收容栏。 |

按事件的主要贡献归类，不能按来源网站归类。同一事件只在最匹配方向出现一次；一篇文章可以引用多个来源，但不得把一份发布说明拆成多个条目。其他方向需要时在正文中交叉链接。

## 条数、时效与选题组合

- 前七个专题各优先 3—5 条；快讯按价值选 0—5 条，不设最低条数。全期最多 40 条，数量不构成保底任务。证据不足时允许某方向 0—2 条，在 `coverage` 中写明数量及具体原因；0 条写“本期未发现可核实的新进展”或准确的检索覆盖限制。全部无可用条目时不提交空日报，报告核验结果。每个方向的 `coverage.note` 均简记真实查过的代表性机构/入口、来源角色、时间窗、排除/读取失败及重要待跟进项，即使达到三条也记录，最多600字。未搜索到、不能读取、读完无新增和重复/低价值应分开，未读不计作已核查。缺稿说明不充作文章，仅存于 `coverage.note` 供内部核验，不放入新闻标题、摘要、正文、网页、邮件或机器人消息。
- 首选运行时点前 24 小时的新发布或实质更新，必要时扩至 72 小时、最多 7 天。不能把网页抓取日期、转载日期或检索日期当成事件日期。国际时区统一换算后判断时间窗，保留原始来源日期与版本更新日期。
- 7 天以外仅在当期新事件需要背景时引用；不再用无变化的旧论文/旧草案填满配额。如确有值得首次介绍的较早工程成果，可少量作为明确标记“技术回顾”的独立选编，但全期最多 2 条，每方向最多 1 条，且不能重复本站已报道事件。没有合格新稿宁可少报。
- 算法栏目不设纯论文硬上限，也不要求非论文或实现发布的最低数量。先分别检索学术、企业算法研发、政府/评估与实现四类来源，再按技术贡献和新闻价值排序。论文不要求已有代码、产品或生产部署，附代码也不能改标成第二个独立工程事件。有价值的实现、国内密码库正式发布、软硬件测试仍纳入，但不能由库的小修复代替算法方向。连续7期复核来源与事件类型，集中时先补查缺口；不为配比牺牲更重要的研究，也不因可读代码较多而机械偏重实现。
- 协议栏目优先覆盖实现发布、互通/性能测试、部署/故障、安全分析中至少两种事件类型。仅草案版本或 RFC 流程变化统一归标准栏目，不用改写标题规避。缺少支撑核心机制、安全或工程主张的原始证据时减少条数并说明；实质协议机制/安全证明研究不因没有代码而排除，不得用5个仅有状态变化的草案拼成协议日报。
- 迁移栏目同时关注公司方案与工程进展，以及采用方和行业组织的需求、试点、采购/验收条件、真实部署、失败和回滚；实际阅读官方技术博客、架构文档、白皮书、发布说明和公开案例；主动检索国内密码企业、云厂商、运营商及海外相关企业。不能仅因尚未生产上线或没有代码发布而排除有实质技术内容的新方案；厂商宣称与独立验证分开，没有技术细节的合作签约、营销口号不单独成稿。旧方案仍须遵守时效与去重规则，无实质变化不得重报。AI 栏目优先至少两种事件类型。单栏至少3条且有足够来源时，避免同一机构/项目占单栏过半；超过时必须补查尚未检查的其他相关来源并比较候选，当日有效检查可复用。若确有重大新闻集中发生，可保留并在coverage说明证据与理由。数量和类型偏好不得凌驾于真实性、价值和去重。
- 国内外投入相同检索关注，主动检索中文主管部门、标准组织、科研机构、开发团队及厂商，同时检索海外一手来源；按来源归属和研发主体的明确信息判断，不从姓名推断国籍。审查连续 7 期是否长期偏向单一地区、机构或事件类型；无需机械各占一半，不为平衡添加无价值内容。
- 从最近 7 期开始建立事件清单，必要时查最近 30 天；对候选选题检索更早报道。比对事件主体、版本、CVE/finding ID、标准编号与版本及原始 URL，不仅比对标题/slug。改标题、换转载或切换同一论文 HTML/PDF 不算新事件。再次报道必须明确相较前次发生了什么实质变化，并链接前文。

## 候选发现与检索范围
按 news/source-guide.md 的来源角色开展检索，该清单是开放入口，不是报道白名单。先用中英文主题词＋事件动作（研究/证明/攻击/评估/发布/试点/部署/事故/回滚/修复/撤回/征求意见/许可证或成本变化）做不限定机构的搜索，再定向查相关发布方和原始材料；使用算法/协议全称、缩写、中文名、旧名、版本号和文档号补检。不要一开始只翻wolfSSL、vLLM或固定几个GitHub仓库的commit；找到3条后也必须完成该栏主要来源类型的扫描。
每栏至少检查两种与该栏目相关的来源角色，并覆盖中文与海外线索；算法分别检查学术、企业研发、政府/评估与实现，迁移分别检查供给方方案和用户/行业组织实践，安全检查应急/PSIRT和实际事件/研究，AI检查模型/产品、研究/独立评测及应用/产业。没有材料可读时如实记录限制，不能伪称完成；这是检索义务，不是发稿配额。
国内外投入同等检索关注；海外按相关性覆盖欧洲/英国、北美和其他亚太地区，必要时查当地原文，不把“国外”等同美国。核心扫描指按来源角色选取的代表性索引/公告/发布入口与必查NGCC入口，具体全文依据候选深入。扩展来源按近7期缺口轮换，同一来源/时间窗的有效检查跨栏复用，不机械重复查询或声称遍历全清单。RSS/Atom、公开API、会议日程、邮件列表、数据库、媒体、社区和社交平台可用于发现，全文核验后才成稿。采用公开、实际可用的入口，不猜订阅地址，不绕过访问控制。

## 新闻价值与来源集中复核
先排实质性算法/安全结论、重要标准与政策节点、具有具体适用价值的产品/方案/部署、显著攻击/事故及可复现测量，再考虑日常维护。单个commit/PR须由原始报告、issue、回归测试或实测明确实际受影响行为/范围、重要算法能力或可量化的显著性能变化，才考虑独立成稿；不能仅凭diff推演安全影响。日常加固、测试扩充、兼容小补丁原则上并入相关版本更新，重大新问题不必等待CVE编号或正式发行；日志、UI文字、重命名、零散测试、普通重构和边界清理不因有代码就入选。具有同一原因和影响的连续提交/修复合并为一个事件，发行新闻不能重复包装已报提交；不以读者对某技术的熟悉程度代替新闻价值。
在写稿前按研究机构/企业/项目、来源角色、事件类型和地区检查当期及近7期组合；GitHub、arXiv是托管平台，不等于一个机构，同集团多域名也不等于独立来源。某栏样本至少3条时，若同一机构/项目超过半数，或最近7期一类事件持续支配该栏，必须补检尚未检查的缺失类型并比较被放弃的高价值候选；当日已对同一缺口有效检索可复用结果；不得仅写“已注意多样性”。有充分重大性理由可保留集中报道并在coverage记录，不为分散强塞低价值新闻。

## 一手阅读、核验与正文

先建立候选清单再写正文。一手性按具体事实的直接来源判断：算法证明、技术规格、标准状态、修复结论必须追原论文、正式记录、研究者原始报告或维护者资料；原创采访、文件调查、现场报道和原始独立评测也可支持其直接揭示的事件事实。媒体原创报道可担任主来源，其转述的技术结论仍追原始材料；转载、聚合与搜索/论文摘要只能找线索，不充作全文。

每篇实际读取支持核心事实的全文、发布记录、附件、必要代码或实验材料，记下日期、版本、证据、限制和前次报道。官方/厂商声明与独立验证分开；关注失败、负面结果、公开回应、争议、修订和撤回。重大安全、性能、部署主张主动查独立验证和已公开回应；只有单方证据时明确归因，不以多个转载冒充交叉验证，不伪称已联系当事人或执行实验。

source_url指向直接支持核心事件的具体HTTPS原始发布、原创调查或原始评测页面；正文在相关事实处添加其他关键证据的Markdown链接，可在末尾简列来源及日期，不自行添加接口字段。研究、模型和标准用各自所需证据，不能因政策/行业事件没有代码或白皮书就排除。

遇到403、空正文、失效PDF或页面迁移，先查官方新入口、附件、作者公开全文或可信机构仓库等合法替代；仍不可读时记录具体失败与待跟进线索。检索日期、抓取日期及无实质内容变化的页面刷新不当新闻日期，不把读取失败概括为该领域没有新闻。

前七个专题摘要为 100—180 字中文导语。详情通常 600—1600 字、至少 5 个实质段落，采用新闻网站连续长文；以新闻事实和意义组织多来源核实后的中文综述，交代事件、机制/方法、数据口径、适用条件及局限，再用独立标题 `## 量仔观察` 写本站总结与研发分析。开头写 ISO 原始来源日期，例如“原始来源：2026-10-09；版本更新：2026-10-10”。研究、产品、迁移、漏洞和标准使用各自相关证据，不能机械套同一模板。

事实、作者主张和本站判断应清楚区分。性能必须说明参数集、硬件、软件版本、基线、测量指标和适用条件；未知就写未知，不能拼接不可比数字。部署要区分公告、试点与生产上线，代码合并不等于发行。安全分析要区分理论/实验、经典/量子代价及时间/内存/查询/电路模型；缺少证明不等于已经破解。标准条文、技术机制及修订内容的结论须读取正式全文/差异；仅报道编号、采纳、批准、发布等状态事实时，可依据实际阅读的Datatracker/RFC Editor/国内官方状态记录，不能推断未读条文或凭新闻标题断言已发布。

遵守许可与引用限额，按每一来源遵守当次引用/归纳限额，默认用自己的语言独立组织事实和分析、保留可点击入口，不将单一媒体稿近似全文翻译；仅在许可确实允许时作全文翻译。不得用重复段落、换词复述摘要、通用建议或无证据的背景满足 600 字。重要短公告先纳入候选，核实同一事件的原始资料、适用对象和影响依据；事实完备但无需长篇分析时归入同级flash栏目，summary为40—180字符、content为80—599字符，通常1—3段，开头同样写ISO原始日期并给具体HTTPS来源，不要求五段或“量仔观察”。核心事实未核实的线索仍记录在coverage待跟进。短稿与长文不重复同一事件；日后扩成长文须有实质新增并链接前文。不以原文长度决定新闻价值，不把低价值条目转入快讯或把无关短讯拼成长文。可以给出与具体证据相关的复现或测试方向，但不能宣称已经执行未执行的实验。

## NGCC 专项核验

官方流程以 https://www.niccs.org.cn/ 及实际公钥征集页面为准。每次还需从官方通知、算法提案与算法评议追候选方公开规格、回应及修订，并检查用户指定的 https://ngcc.dev/、https://ngcc.dev/reports/index.html 和 https://ngcc.dev/report-classification.html，并按需读 Performance、Side-Channel、具体发现详情、原始规格/仓库和提交者公开回应。详情入口做 `source_url`，索引页只作导航。

ngcc.dev 是独立分析站，不是 ICCS 官方评审结果。逐条记录候选编号/名称、参数集、规范或实现版本、稳定 finding ID、原始/更新日期、Credit 中的实际发现者，以及本次新增、状态变更、修复、复测、撤回或争议。不能把全部发现归于网站维护者。同一发现的网页、同作者论文和其代码可能是一条证据链，不得机械计作多个独立验证来源。

严格区分 Severity、Status、Layer。来源标记 Confirmed 不等于本站独立复现；Lead / Proof gap 不可写成已攻破。说明攻击前提、设计/实现/侧信道层面、影响安全性质、声称安全级别、复杂度口径、实际可执行性与未验证环节。源码秘密相关分支、测量到泄漏和端到端密钥恢复分别表述。低于声称安全级别的理论攻击不一定能现实实施；提出修复不等于完成验证，旧版发现不能无条件套用新版。未公开的回应不作为可公开核实事实。

## 提交前编辑复核

检查八栏数量、稿件体裁与真实覆盖记录、事件与原文去重、新闻价值、算法/协议/安全/AI的事件组合、来源机构/类型/地区集中性、日期/版本/状态、正文实质段落、引用权限和分析针对性。AI补查模型卡/系统卡、权重/API/许可证、真实可用阶段、原始评测和影响采用的产业/政策；安全补查应急/PSIRT、攻击与事故、受影响机构回应。PoC、理论可利用、确认在野利用、KEV收录、EPSS概率和CVSS严重度不可互换，普通bug不自动等同安全漏洞。`news/validate-edition.py` 仅证明结构合格，不证明事实、版权或选题质量已通过。不能用“校验通过”替代逐条阅读和事实核查。

## 事件优先级与每周回顾

日报与周报采用同一分级：P1重大（可靠证据、广泛影响或需要及时行动）；P2重要（明确研发、标准或采用价值的实质进展）；P3关注（真实新增但影响有限、尚早或需持续观察）。每条用priority_reason解释具体理由；优先级与证据成熟度分开，不等同CVSS或来源自己的Severity，不按机构、地区或固定比例分级。日报从2026-10-22执行，各栏按P1→P2→P3排列。

周五周报按八栏目独立检索过去七天，以主体、版本、标准编号、论文或finding ID合并连续进展，写清一周前状态、本周新增与当前结论，不能拼接日报或把相同论文/发行重复计数。头版头条可以多个，须为P1或有充分理由的P2；其余事件只列在各栏目，头条不重复，缺稿不凑数。周报与日报同样核对来源、日期、关键证据及局限，标记早期主张，记录检索限制。
